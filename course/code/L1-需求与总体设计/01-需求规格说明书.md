### 1.5 术语与缩略语

| 术语 | 定义 |
|---|---|
| 模型（Model） | 仅完成"文本输入—文本输出"变换的大语言模型，不具备任何环境访问或行动能力 |
| Harness | 围绕模型构建的完整系统，提供工具、循环、上下文、权限与沙箱 |
| Turn | 一次完整的任务周期：用户提交任务起，至 Agent 给出结论止 |
| Step | Turn 内部的一次模型调用及其引发的工具执行 |
| 上下文（Context） | 单次模型请求所携带的全部内容，含 system 段、历史消息、检索结果与当前输入 |
| 工具（Tool） | 由 Harness 提供、可供模型请求执行的能力单元 |
| 原语（Primitive） | 不可再拆分的基础能力单元，通过组合表达复杂行为 |
| observation | 回喂给模型的工具执行结果，含失败结果 |
| 沙箱（Sandbox） | 由操作系统内核提供的强制访问控制机制 |
| 权限门（Gate） | 位于应用层、在工具执行前进行授权判定的机制 |

## 2. 系统概述

### 2.1 产品定位

AgentForge 是一个面向代码仓库的编码 Agent Harness。系统在真实代码仓库中
接收自然语言任务，通过工具自主获取信息、修改代码、执行命令并验证结果，
在多步执行后给出结论。

与对话式系统的区别在于：系统具备观测环境、改变环境、根据执行结果
决定下一步动作三组能力，动作序列由模型在运行期决定，而非预先编排。

### 2.2 涉众与用户特征

| 涉众 | 特征 | 对系统的要求 |
|---|---|---|
| 开发者（主要使用者） | 熟悉命令行与版本控制；以完成工程任务为目标 | 任务完成率、执行可中断、过程可见 |
| 系统维护者 | 负责 Harness 本身的演进 | 模块边界清晰、扩展无需改动核心 |
| 插件开发者 | 以第三方动态库扩展工具 | 接口稳定、跨编译器可用 |
| 安全评审人员 | 审查越权与数据泄露风险 | 策略可枚举、判定可审计 |

### 2.3 运行环境

| 类别 | 要求 |
|---|---|
| 操作系统 | Windows 10 及以上；Linux（内核 5.13 及以上，需 Landlock）；macOS 12 及以上 |
| 语言与标准 | C++20 |
| 硬件 | 无特殊要求；内存占用受仓库索引规模影响 |
| 网络 | 可选。连接模型服务时需要；本地验证可在无网络条件下进行 |
| 第三方依赖 | nlohmann/json（必需）；tree-sitter、FTXUI（可选，缺失时降级） |

### 2.4 系统边界与外部实体

系统边界由四个外部实体界定，四者均不受本系统控制，其变化必须可被隔离：

| 外部实体 | 不可控因素 | 隔离要求 |
|---|---|---|
| 模型服务 | 协议不统一、限流、超时、版本演进 | 经 `IModelProvider` 端口隔离 |
| 网络 | 连接失败、代理、TLS 差异 | 经 `IHttpTransport` 端口隔离 |
| Shell / 子进程 | 可执行的命令集合不受限，输出内容不可信 | 经 `ISandbox` 端口隔离，输出须消毒 |
| 用户 | 输入不可预测，授权决策不可预知 | 经 `IUIPort` 端口隔离 |

### 2.5 功能边界

以下事项明确不包含在需求范围内：

| 排除项 | 说明 |
|---|---|
| 模型训练与微调 | 模型能力由外部提供，不在本系统职责内 |
| 多智能体协作平台 | 子代理仅作为上下文隔离手段，不作为协作范式提供 |
| Web 服务形态 | 仅保留 `IUIPort` 端口，不实现服务端 |
| 通用代码生成能力 | 生成能力由模型提供，本系统提供执行与约束 |

## 3. 功能需求

### 3.1 功能需求汇总

| 标识 | 名称 | 优先级 | 稳定性 | 承载模块 | 实现阶段 |
|---|---|---|---|---|---|
| FR-1 | 任务理解与信息定位 | 高 | 稳定 | ⑦ 循环、⑥ 工具、③ 索引 | L5 / L4 / L8 |
| FR-2 | 代码修改 | 高 | 稳定 | ⑥ 工具 | L5 |
| FR-3 | 命令执行与结果读取 | 高 | 稳定 | ⑥ 工具、⑧ 沙箱 | L5 / L6 |
| FR-4 | 多步自主循环 | 高 | 稳定 | ⑦ Agent 循环 | L5 |
| FR-5 | 中断与恢复 | 中 | 稳定 | ⑦ 循环（闸门 6）、⑫ 存储 | L6 / L10 |
| FR-6 | 执行过程可观察 | 中 | 稳定 | ⑪ UI、⑨ 可观测性 | L9 / L12 |
| FR-7 | 危险操作可控 | 高 | 稳定 | ⑧ 权限门、⑧ 沙箱 | L6 |
| FR-8 | 失败可恢复 | 高 | 稳定 | ⑦ 循环、⑥ 工具 | L5 / L6 |

> FR-4 是本系统与对话式系统的分界需求。缺少 FR-4，其余需求仅构成
> "接入模型的程序"，不构成 Agent。

### 3.2 功能需求详述

#### FR-1 任务理解与信息定位

系统应接收自然语言任务，并通过工具主动获取完成任务所需的信息
（读取文件、检索符号、查看目录结构），不得仅依据任务描述直接作答。

- **输入**：自然语言任务描述。
- **处理**：将任务置入上下文；由模型决定所需信息并请求相应工具；工具结果回写上下文。
- **输出**：基于已获取事实的结论或后续动作。
- **验收判据**：给定"统计 `src/a.cpp` 中的函数数量"类任务，系统在作答前
  必须产生至少一次读取类工具调用；未产生工具调用即作答的，判定不通过。

#### FR-2 代码修改

系统应能新建文件，并对已有文件执行精确修改，不得以整文件重写替代局部修改。

- **输入**：修改目标与修改意图。
- **处理**：定位待修改片段，生成精确替换；替换前校验目标片段在工作区中唯一。
- **输出**：文件内容变更，变更范围限于目标片段。
- **验收判据**：给定"将标识符 `foo` 重命名为 `bar`"，文件实际内容发生变更，
  且与目标片段无关的行未被修改。

#### FR-3 命令执行与结果读取

系统应能执行构建、测试、版本控制等命令，并将命令输出（含失败输出）
作为可用信息纳入上下文。

- **输入**：待执行命令及其参数。
- **处理**：在沙箱约束下执行，采集标准输出、标准错误与退出码。
- **输出**：结构化执行结果，回写上下文。
- **验收判据**：给定"修复失败的单测"，系统须完成"运行测试—读取失败信息—
  修改代码—再次运行"的完整序列。

#### FR-4 多步自主循环

系统在无需人工逐步指令的条件下，应能连续执行多个步骤，直至任务完成
或满足终止条件（见 NFR-1 与《总体设计说明书》§9 出错处理设计）。

- **输入**：用户提交的任务。
- **处理**：重复执行"模型调用—工具执行—结果回写"，终止条件由模型无工具调用
  或闸门触发决定。
- **输出**：任务结论，及完整执行轨迹。
- **验收判据**：单次任务提交后，系统在无人工干预下自主完成不少于三次工具调用。
- **说明**：该需求与 FR-5、FR-8 共同构成循环内核的约束集合。

#### FR-5 中断与恢复

用户应能随时中断执行中的任务；中断后应能从上一次会话继续。

- **输入**：中断信号；恢复指令。
- **处理**：中断时终止当前工具调用并保留已完成步骤；恢复时重建上下文。
- **输出**：中断时的已完成步骤摘要；恢复后的续执行。
- **验收判据**：执行过程中触发中断，当前工具调用被终止且已完成的步骤被输出；
  再次启动并指定恢复参数后，任务在原上下文上继续。

#### FR-6 执行过程可观察

系统在每一执行步骤应输出当前工具调用、参数、结果与资源消耗。

- **输入**：执行过程中的内部事件。
- **处理**：将内部事件转换为可呈现事件并输出。
- **输出**：连续的过程输出。
- **验收判据**：执行过程中不存在无输出的等待区间；超过 2 秒的操作须有进度指示。

#### FR-7 危险操作可控

对可能造成不可逆破坏的操作（删除、推送、修改工作区外文件），
系统应在执行前取得授权，或被强制机制拦截。

- **输入**：模型请求执行的工具调用。
- **处理**：权限门判定授权；沙箱执行强制访问控制。
- **输出**：放行执行，或返回拒绝结果及可解释原因。
- **验收判据**：请求执行 `rm -rf /` 类破坏性命令时，操作被拒绝，
  且拒绝原因以模型可理解的形式回喂，模型据此改用其他方式继续任务。

#### FR-8 失败可恢复

工具执行失败、模型请求失败、参数不合法均不得导致会话终止；
失败信息应以 observation 形式回喂模型，使其可自行修正。

- **输入**：任一环节的失败。
- **处理**：捕获失败，转换为携带原因的 observation，回写上下文。
- **输出**：继续执行或终止并给出结论。
- **验收判据**：人为使某一工具报错后，系统读取错误信息、改用其他方式重试，
  任务仍可完成。

## 4. 非功能需求

非功能需求决定模块的内部结构，其优先级高于功能需求的逐条枚举：
功能需求决定模块的划分，非功能需求决定模块的实现方式。

需求按 ISO/IEC 25010 质量特性模型归类。

### 4.1 非功能需求汇总

| 标识 | 名称 | 质量特性 | 优先级 | 稳定性 | 承载模块 | 实现阶段 |
|---|---|---|---|---|---|---|
| NFR-1 | 不造成破坏 | 安全性 | 高（不可降级） | 稳定 | ⑧ 权限门、⑧ 沙箱 | L6 |
| NFR-2 | 成本可控 | 性能效率（资源利用） | 高 | 稳定 | ④ 上下文、② 缓存 | L7 |
| NFR-3 | 可审计 | 可维护性（可分析性）、可靠性（可追溯性） | 中 | 稳定 | ⑫ 存储、⑨ 可观测性 | L10 |
| NFR-4 | 响应体验 | 性能效率（时间特性）、易用性 | 中 | 稳定 | ⑪ UI、② 流式 | L3 / L9 |
| NFR-5 | 可扩展 | 可维护性（模块性、可修改性） | 高 | 稳定 | 全部端口 | L2 起 |
| NFR-6 | 可测试 | 可测试性 | 高 | 稳定 | 假服务端、协议隔离 | L3 |

### 4.2 NFR-1 不造成破坏

系统在任何情况下不得对授权范围之外的资源造成不可逆影响。该需求不接受
降级满足：出现一次越权写入即判定系统不合格。

| 项 | 要求 |
|---|---|
| 默认姿态 | 最小权限：默认仅可读写工作区，无网络访问 |
| 危险操作 | 须同时经应用层授权门判定与内核层强制机制约束 |
| 可回滚 | 文件修改前可生成检查点并支持还原 |
| 泄露防护 | 只读操作同样受约束，禁止读取密钥类文件 |

**推导出的设计**：权限门（应用层）与沙箱（内核层）的双层结构，见 ADR-4。

### 4.3 NFR-2 成本可控

模型调用成本应可预测、可归因、可解释。

| 项 | 指标 | 手段 |
|---|---|---|
| 提示缓存命中率 | 长会话中不低于 60% | 缓存前缀保持字节级稳定，消息顺序与内容不得随意变动 |
| 单轮上下文增量 | 单次大工具输出引入的增量不超过 2 KB | 大结果落盘，仅保留预览 |
| 成本可见性 | 每轮可报告累计消耗 | 分层记账，提供 `/cost` 查询 |
| 压缩触发 | 仅在接近窗口上限时触发 | 预算阈值结合抖动保护，避免边界振荡 |

**推导出的设计**：上下文分层组装（ADR-5）、压缩级联、大结果落盘。

### 4.4 NFR-3 可审计

每一 Turn 的消息、工具调用、资源用量与权限判定结果应可持久化并完整回放。

- **验收判据**：给定一份会话记录文件，可完整重建 Agent 当时的上下文与决策依据。

### 4.5 NFR-4 响应体验

| 指标 | 目标 |
|---|---|
| 首 token 时间 | 采用流式输出，不等完整响应后再呈现 |
| 界面流畅度 | 流式输出期间界面不阻塞，渲染与执行分离 |
| 长任务反馈 | 超过 2 秒的操作须显示进度 |

### 4.6 NFR-5 可扩展

扩展系统能力时不得修改核心模块源码。

| 扩展点 | 要求 |
|---|---|
| 更换模型厂商 | 新增一个适配器文件，核心改动量为 0 |
| 增加工具 | 新增一个文件并注册一次，核心改动量为 0 |
| 更换平台 | 新增一个传输实现与沙箱实现 |
| 更换界面 | 新增一个界面实现 |

该需求是端口与适配器结构的来源。其违反通常不在编译期暴露，
检验方法为：若新增一个工具需要修改 `agent_loop.cpp`，即判定违反 NFR-5。

### 4.7 NFR-6 可测试

协议层逻辑（SSE 分帧、工具参数累积、压缩切点）应能在不连接真实模型服务、
不产生调用成本的条件下测试。

- **手段**：提供可注入的假服务端（`mock_server.py`），其行为可编排。

## 5. 设计约束

以下约束不可协商，需求与设计均须在其前提下成立。

| 标识 | 约束 | 对设计的影响 |
|---|---|---|
| C-1 | 上下文窗口存在硬上限（典型值 128K–200K token，随模型而定） | 必须实施预算管理与压缩 |
| C-2 | 模型输出存在错误、幻觉与重复调用的可能 | 失败须表达为 observation；须具备重复调用检测 |
| C-3 | 工具输出规模可能远超窗口容量 | 须落盘并仅保留预览，参见 NFR-2 |
| C-4 | 外部字节流的编码不可信（源文件可能为 GBK，命令输出可能含控制字符） | 进入上下文前必须消毒 |
| C-5 | 网络不可靠，存在限流、网关错误与超时 | 须实现重试、指数退避与抖动 |
| C-6 | 须支持 Windows / Linux / macOS 三个平台 | 传输层与沙箱必须可替换 |
| C-7 | 模型输出格式不完全可控 | 全部解析逻辑须容错，包括半截 JSON 与格式偏离 |

> C-4 与 C-7 已在实现阶段 L3 与 L4 各实际触发过缺陷，属已验证的风险，
> 非理论风险。C-4 的处置由"约束"升级为强制防线，见附录 A 变更记录。

## 6. 外部接口需求

### 6.1 用户接口

命令行交互：接收任务输入与指令，输出流式文本、工具执行状态、
差异对比与授权请求。接口实现可替换，见 NFR-5。

### 6.2 模型服务接口

- **协议**：HTTP，支持 OpenAI 兼容的 `/chat/completions` 与 Anthropic 的 `/messages`。
- **传输**：支持流式（SSE）与非流式两种模式。
- **能力**：须支持 function calling / tool use。
- **约束**：计量数据以服务端返回为准，客户端估算不作为结算依据（参见 C-5）。

### 6.3 文件系统接口

- **访问范围**：默认限于工作区目录；工作区外的读写须显式授权。
- **编码**：读取时按探测结果转换为 UTF-8；写入时保持目标文件原有编码约定。
- **约束**：密钥类文件的读取应被拒绝（参见 NFR-1）。

### 6.4 子进程接口

- **执行方式**：以子进程执行命令，采集标准输出、标准错误与退出码。
- **约束**：执行须在沙箱约束下进行；子进程输出属不可信外部字节流，
  须经消毒后方可进入上下文（参见 C-4）。
