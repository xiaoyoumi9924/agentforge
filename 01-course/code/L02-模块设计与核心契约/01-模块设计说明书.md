## 1. 引言

### 1.1 编写目的

本文档规定系统中各模块的职责边界、对外提供的接口、允许依赖的对象，
以及跨模块共享的类型与不变式。实现人员依据本文档可确定：

- 某段代码归属于哪个模块；
- 该模块可以依赖哪些模块、不得依赖哪些模块；
- 接口的输入与输出采用哪些类型；
- 失败以何种形式表达。

### 1.2 适用范围

本文档覆盖 13 个功能模块与 1 个契约层（共 14 项）的接口契约，
以及由各实现阶段增补的契约不变式。
各模块内部算法的实现细节不在本文档范围内，由对应阶段的讲义与源码给出。

### 1.5 术语与缩略语

| 术语 | 定义 |
|---|---|
| 契约（Contract） | 模块对外承诺的接口形状、类型与不变式 |
| 契约层 | `types.hpp`，为全部模块提供共享类型，不依赖任何项目内文件 |
| 端口（Port） | 由核心层定义的抽象接口，用于隔离不受本系统控制的外部实体 |
| 不变式（INV） | 必须恒真且被机械校验的性质；违反后常在远端或后续轮次才显现 |
| 契约级伪码 | 中文描述 + 类 C 结构，仅表达接口形状与不变式，不表达完整算法 |
| 算法级伪码 | P1–P11，表达完整流程，在对应阶段给出（见 §8.2） |
| 实施阶段 | 项目实现按 L1 至 L12 推进，本文档以该标识标注引入阶段 |

### 1.6 三条契约规矩（全文准则）

以下三条约束本文档全部接口定义，后续每阶段的接口讨论均以三者为判据。

| 规矩 | 内容 |
|---|---|
| **CR-1** | 共享类型置于 `types.hpp`，接口置于各自模块的头文件 |
| **CR-2** | 失败以返回值表达（`isError` / `ErrorChunk`），不以异常表达 |
| **CR-3** | 接口只增不改；本阶段刻意留空的成员以注释标出 |

### 1.7 伪码约定

本文档使用**契约级伪码**（中文描述 + 类 C 结构），
仅表达"接口形状与不变式"，不表达完整算法。
完整算法伪码（P1–P11）在对应阶段给出，对照表见 §8.2。

## 2. 模块清单与分层

### 2.1 三个层次

层次依变化频率划分，变化越慢者越稳定，位于越下层。

| 层 | 稳定性 | 本层可以依赖 |
|---|---|---|
| 交互执行层 | 最低（界面与工具频繁变动） | 核心智能层、基础设施层、契约层 |
| 核心智能层 | 中（协议与策略按季度变动） | 基础设施层、契约层 |
| 基础设施层 | 高（JSON、日志、存储几乎不变） | **仅契约层** |
| 契约层（`types.hpp`） | 最高 | **无**（不依赖任何项目内文件） |

### 2.2 归属表（13 模块 + 契约层）

| 层 | 编号 | 模块 | 物理落点（最终） | 引入/兑现阶段 |
|---|---|---|---|---|
| 交互执行 | ⑥ | 工具调用与执行 | `tool_registry.{hpp,cpp}` | L2 声明 / L4 实现 |
| | ⑪ | UI 与交互 | `ui/*` + `IUIPort` | L2 声明 / L9 实现 |
| | ⑬ | 测试与评估 | 回归脚本 + `trace` 消费端 | L12 |
| 核心智能 | ⑦ | Agent 循环 | `agent_loop.{hpp,cpp}` | L2 声明 / L5 实现 / L6 加闸门 |
| | ② | 多模型适配 | `providers.cpp` + `sse_parser.*` | L2 声明 / L3 实现 |
| | ④ | 上下文组装与优化 | `context_budget.{hpp,cpp}`、`compaction.*` | L2 声明 / L7 实现 |

| **契约** | ⓪ | **类型契约** | **`types.hpp`** | **L2** |

### 2.3 模块归属判据

模块归属的判据是"该模块依赖什么、知道什么"，而非"谁调用它"。
据此，⑧ 安全与权限与 ⑫ 持久化与记忆归入基础设施层：

| 模块 | 它认识什么 | 它不认识什么 | 因此归属 |
|---|---|---|---|
| ⑧ 沙箱 | 操作系统原语（Landlock / Seatbelt / Job Object） | 循环、界面、具体工具语义 | 基础设施 |
| ⑧ 权限门 | `(ToolDef, args)` 抽象 | 任何具体工具、界面实现 | 基础设施 |
| ⑫ 会话存储 | JSONL / SQLite | 循环、界面 | 基础设施 |

将上述模块置于下层，可使更换界面实现不影响沙箱、更换沙箱实现不影响循环。

## 3. 契约层：`types.hpp`

契约层不是一个功能模块，而是全部模块共用的类型语言。
它定下 12 条契约层不变式（见 §7.1），由 `contract_check.cpp`
在编译期与运行期强制校验。

后续阶段增补的不变式（§7.2，如 L7 的 INV-13/14/15）
不属于契约层文件本身，而属于"新能力引入的新规矩"，
由对应阶段的 `--selftest` 与 `verify.ps1` 守着。

### 3.1 类型清单

| 类别 | 类型 | 说明 |
|---|---|---|
| 基础 | `Role` / `FinishReason` / `RiskLevel` / `ToolChoice` / `Layer` / `LoopOutcome` / `Degrade` | 全部 `enum class`（禁隐式转 int） |
| 消息 | `Message`、`ToolCall`、`Usage` | 值语义，非多态 |
| 工具 | `ToolDef`、`ToolResult` | 值语义 |
| 事件 | `ChatChunk` = `std::variant<8 种>` | 穷尽处理由编译器保证 |
| 请求响应 | `ChatRequest`、`ChatResponse` | 值语义 |
| 循环 | `LoopLimits`、`Turn` | `Turn` 必须在此（CR-1，见 §7.1 的 INV-12） |
| 预算 | `BudgetConfig` | 分层配额 |
| 压缩 | `CompactionEvent`（L7 新增） | 一次压缩的事件记录：级别 / 前后 token / 说明 |
| 卫生 | `isValidUtf8` / `sanitizeUtf8` / `overloaded`（L2）｜`utf8Snap` / `utf8Prefix` / `utf8Resize`（L7） | 内联函数与工具 |

### 3.2 关键不变式（摘要）

| # | 不变式 | 违背后果 |
|---|---|---|
| INV-1 | `ChatChunk` 恰好 8 种事件 | 漏处理某类事件（静默失败） |
| INV-2 | 端口必须是抽象类，不可实例化 | 核心与实现耦合 |
| INV-3 | `Message` **非多态** | 拷贝热路径性能下降 |
| INV-4 | 枚举均为 `enum class` | 参数误传（`int` 隐式转换） |
| INV-5 | `RiskLevel` 单调递增：Read<Write<Exec<Network | 权限门"至少 Write 级"判断失效 |
| INV-6 | 各层预算之和 + 历史 = 可用量 | 预算溢出或欠分配 |
| INV-7 | `sanitizeUtf8` 输出必为合法 UTF-8 且合法输入幂等 | JSON 序列化抛异常 |
| INV-8 | `ChatRequest.tools` 顺序字节级稳定 | 提示缓存永不命中 |
| INV-9 | `ToolResult.callId` 必须匹配某个 `ToolCall.id` | 结果错配 |
| INV-10 | `Usage::total()` 含 cache 读写 | 压缩触发条件失效 |
| INV-11 | 空的 tool 内容必须替换为占位符 | 部分 provider 拒绝 `content=""` |
| INV-12 | `Turn` 定义在契约层 | 循环依赖 |
| **INV-13** | **压缩切点绝不落在 `tool_result` 处**（L7） | 造出孤儿 `tool_result` → 请求 400 |
| **INV-14** | **降级链单调，且绝不返回残缺内容**（L7） | "半个函数"属有害内容，模型据此误判 |
| **INV-15** | **摘要失败必须降级，不得抛异常**（L7） | 一次摘要失败拖垮整个循环（违反 CR-2） |

完整说明见 §7。

## 4. 基础设施层 · 模块契约

### 4.1 ⓪ 类型契约（`types.hpp`）

| 项 | 内容 |
|---|---|
| **职责** | 定义全工程共享的数据结构、枚举、文本卫生函数 |
| **对外提供** | 类型定义；`isValidUtf8` / `sanitizeUtf8`；`overloaded`；`Usage` / `Message` / `ToolResult` 的行为方法 |
| **依赖** | 仅标准库 + `nlohmann/json.hpp` |
| **不做什么** | **不依赖任何项目内文件**（该约束是其定义性约束） |

```
契约级伪码 —— 文本卫生（唯一有实现的部分）
──────────────────────────────────────────
function sanitizeUtf8(bytes) -> string:
    if isValidUtf8(bytes): return bytes          // 快路径：绝大多数内容合法
    out = ""
    while 还有未处理的字节:
        n = 按首字节判断该码点占几个字节
        if 该码点完整且后续字节都是续接字节(10xxxxxx):
            out += 该码点; 前进 n 字节
        else:
            out += U+FFFD;  前进 1 字节            // 非法字节替换，绝不抛异常
    return out
```

**规则**：任何外部字节（命令行参数、文件内容、命令输出）
进入上下文之前必须经此函数处理。该规则属边界约束，不是可选项。

**L7 增补：按字节截断的三个辅助函数（K-21）**

按字节截断是 L2 未预见、L5 埋下、L7 才暴露的一类问题：

```
契约级伪码 —— 边界安全的截断
──────────────────────────────
function utf8Snap(s, i):            // 把下标 i 回退到最近的字符边界
    while i > 0 and s[i] 是续接字节(10xxxxxx): i -= 1
    return i
function utf8Prefix(s, n): return s[0 .. utf8Snap(s, n)]
function utf8Resize(s, n):  return utf8Prefix(s, n) 或按字符数扩容
```

**K-21**：`substr(0, 2000)` 中的 `2000` 是**字节**上限。
中文源码中第 2000 字节通常落在某个汉字中间，直接截断会产生非法 UTF-8，
导致**下一轮**请求的 `json::dump()` 抛出 `type_error.316`。
错误的表现位置与其成因位置不一致。
落点有两处：`compaction.cpp` 的降级截断、`tool_registry.cpp` 的落盘预览截断，
均改用 `utf8Prefix`。
此类问题的处置方式是在边界处修复不变式，而不是等待其在下游暴露。

### 4.2 ⑧ 安全与权限（`sandbox.hpp` + `IPermissionGate`）

#### 4.2.1 `IPermissionGate`（应用层：判定是否需要授权）

| 项 | 内容 |
|---|---|
| **职责** | 对一次工具调用给出 `Allow / Ask / Deny` 判定 |
| **对外提供** | `evaluate(ToolDef, args) → Decision` |
| **依赖** | ⓪（`ToolDef`、`json`）、⑩ 配置（规则来源） |
| **不做什么** | 不认识界面实现、不认识循环、不执行任何操作 |

```
契约级伪码 —— 判定顺序（deny 永远优先）
──────────────────────────────────────
function evaluate(tool, args) -> Decision:
    for rule in rules_ordered_by_kind:      // 保证 deny 段在最前
        if rule.matches(tool.name, args): return rule.decision
    return fallback_                         // 默认 Ask（fail-closed）
```

**不变式**：规则表在构造时即按 `Deny → Ask → Allow` 稳定排序。
即使配置中的书写顺序相反，求值语义也不被破坏。（对应 P-05 责任链）

#### 4.2.2 `ISandbox`（内核层：判定能否强制拦截）

| 项 | 内容 |
|---|---|
| **职责** | 在受限环境中执行命令，并在拦截时**给出可归因的原因** |
| **对外提供** | `exec(command, cwd, timeout) → ExecResult`；`selfCheck(report)`；`config()` |
| **依赖** | ⓪ |
| **不做什么** | 不决定"是否需要请求授权"（该判定属权限门职责） |

```
契约级伪码 —— 执行
───────────────────
function exec(command, cwd, timeout) -> ExecResult:
    if not 沙箱可用(): return blocked("沙箱不可用，拒绝执行")   // fail-closed
    r = 在沙箱约束下派生子进程(command, cwd, timeout)
    r.blockedBySandbox = 是否被策略拒绝
    if r.blockedBySandbox: r.blockReason = 明确原因 + "重试不会改变结果"
    return r
```

**不变式**：`ExecResult` 必须能区分"命令自身失败（`exitCode≠0`）"
与"被沙箱拦截"。若二者不可区分，模型会将拦截误判为命令错误，
从而无限重试同一条命令（见 L6）。

### 4.3 ⑨ 可观测性与日志

| 项 | 内容 |
|---|---|
| **职责** | 结构化记录每个请求的用量、延迟、结果，供审计与成本分析 |
| **对外提供** | `RequestTrace`（结构体）；事件流消费接口 |
| **依赖** | ⓪ |
| **不做什么** | **不参与任何决策**（旁路），不阻塞主流程 |
| **兑现** | L12（埋点形状在此确定：`RequestTrace` 已在 `model_provider.hpp`） |

**L12 兑现形态（`trace.{hpp,cpp}`）**

| 项 | 内容 |
|---|---|
| 类型 | `TraceKind`（event / span 两类）、`TraceEvent`、`Tracer`、`LayerChars`（八层占用） |
| 接入方式 | **`TracingProvider` 装饰器**包住 `IModelProvider` —— **不新增 `LoopHooks` 回调** |
| 容量 | 环形缓冲（`std::deque`，固定容量）；**丢弃条数必须报出来**（`{"dropped":N}`） |
| 落盘 | JSONL，**与 ⑫ 会话日志同一形状**（半行容忍、追加、坏行只丢自身） |
| 默认 | **关闭**（`AF_TRACE=1` 开启）—— 度量本身亦是一种输出 |

**采用装饰器而非扩展 `LoopHooks` 的理由**

1. `LoopHooks` 位于契约层，为埋点破例修改它，`types.hpp` 将不再保持零改动记录；
2. 更根本的原因是：请求由 provider 发出，而非由循环发出。
   TTFT、重试次数、是否被取消、实际请求体大小这四项，
   只有 provider 侧可观测，循环侧均不可见。
   在"请求发生的位置"记录，比在"循环通知的位置"记录更准确。

**三条纪律**（任一条缺失，埋点即由旁路变为干扰源）：

1. **完全透传** —— 不加重试、不加缓存、不修改返回值；
2. **`onChunk` 的返回值必须原样透传** —— `false` 表示调用方请求取消，
   吞掉该返回值会使中断功能与 L6 闸门 6 失效；
3. **关闭时早退** —— 仅判定"不记录"不充分，
   `requestChars()` 仍会完整扫描请求体。

`RequestTrace` 自 L2 起挂在本模块（注释标注"可观测性的基础，L12 会用到"），
它先行确定了"一次请求应记录什么"。该落点预留了 10 个阶段后接入：
良好的设计会将将来要接入的能力预留为一个形状，
而不是预留一段需要猜测的注释。

### 4.5 ⑫ 持久化与记忆（`SessionStore`）

| 项 | 内容 |
|---|---|

#### 4.5.1 兑现形态（L10）

接口按 CR-3"只加不改"落地（原表的三个方法名收敛为一组更贴合 JSONL 的操作）：

```cpp
class SessionStore {
public:
    static std::unique_ptr<SessionStore> open(fs::path dir, std::string resumeId = {});

    // ---- 写（每条都 flush：崩溃最多丢当前事件，不是丢一个缓冲区）----
    void append(const Message& m);
    void appendCompaction(const CompactionEvent& e, int replacedUpto);
    void appendCheckpoint(const CheckpointEvent& e);

    // ---- 读（★ 从一条**可能被截断的**日志里恢复上下文，伪码 P9）----
    LoadResult load() const;

    // ---- 检查点（★ 必须在工具执行**之前**调用：先快照，再改）----
    CheckpointEvent snapshot(const std::vector<fs::path>& files, const std::string& tool) const;
    bool restore(const std::string& checkpointId);

    // ---- 分叉：复制文件就是分叉 ----
    std::unique_ptr<SessionStore> fork() const;

    const SessionMeta& meta() const noexcept;   // ★ resumed 字段：到底有没有接着上
    int seq() const noexcept;                   // 已落盘的最大 seq（compaction 用它当 replaced_upto）
};
```

**三条仅在本阶段成立、且必须写入契约的设计决定**

| # | 决定 | 理由 |
|---|---|---|
| **⑫-D1** | **`CheckpointEvent` 放在 `session_store.hpp`，不进 `types.hpp`** | 只有会话层使用它。与 L9 将 `UiEvent` 置于 `ui/tui.hpp` 属同一判断：按使用范围决定类型归属，不将全部类型集中到契约层。本阶段 `types.hpp` 连续第三阶段零改动 |
| **⑫-D2** | **`replaced_upto` 采用 `seq`（内容判据），不用行号（位置判据）** | 行号会变动（分叉 / 手工编辑 / 后续新增过滤），`seq` 由内容自带，与位置无关。**这是 K-9 的第三次发作**：判据应取 id 或序号，不取位置 |
| **⑫-D3** | **`open()` 若给定 id 则使用该 id，并显式报告 `resumed`** | 静默更换 id 会导致使用者以为在恢复、实际是重开（K-38）。与 L9"降级不是瘫痪"相反的原则：**降级必须声明** |

**半行容忍（追加语义的第四条性质）**

进程被终止时，最后一行缺少换行符。`open()` 应首先检查最后一个字节，
若不是 `\n` 则补写一个 —— 等价于宣告"上一行作废"。
若不作补充，新事件会粘附在坏行上一并作废（K-37）。
修复动作是补充一个字节，而不是回滚整个文件，
这正是 JSONL 相对"整体覆写"的优势。

**三层记忆的落点**

`loadProjectKnowledge()` 读取 `CLAUDE.md` / `AGENTS.md` / `MEMORY.md`，
经 `ContextAssembler::setProjectKnowledge()` 进入 **L1 层**。
该 setter 是 L2 预留的空函数（头文件注释标注"L10 加载"），
与 L8 的 `setRepoMap()` 属同一类处理：
将将来要接入的能力预留为一个空函数，
而不是预留一段需要猜测的注释。

### 5.2 ⑦ Agent 循环（`agent_loop.hpp`）

| 项 | 内容 |
|---|---|
| **职责** | 驱动"推理 → 工具 → 观察 → 再推理"，直至完成或触发停止条件（W2） |
| **对外提供** | `run(Turn&, LoopHooks) → LoopOutcome`；`spentTokens()`；`totalUsage()` |
| **依赖** | ② ④ ⑥ ⑫ ⓪ |
| **不做什么** | 不自行拼装消息（④）、不自行调用 HTTP（②）、不做渲染（⑪） |
| **兑现** | L5（主体）/ L6（六道闸门）/ **L11（递归复用：子代理运行的是同一个 `AgentLoop`）** |

> **★ L11 兑现了一条自 L2 起即成立、至该阶段才被证实的性质：
> `AgentLoop` 是**可递归组合**的，而非全局唯一实例。**
> 子代理不新增任何循环代码 —— 它只是再构造一个 `AgentLoop`，并为其提供一个空的 `Turn`。
> 该性质并非偶然：`run()` 的全部输入均经参数或注入进入（P-16），
> **不存在"全局当前循环"**，因此嵌套不引入附加成本。
> 反之，若循环内存在 `static` 状态或单例，嵌套将无法成立。

```
契约级伪码 —— 循环骨架（完整算法见 L5 的 P1）
──────────────────────────────────────────────
function run(turn, hooks) -> LoopOutcome:
    while true:
        请求 = ④.assemble(turn)                       // 顺序固定，缓存友好
        响应 = ②.stream(请求, onChunk → hooks.onChunk)
        turn.history.append(响应.message)

        if 响应.finish_reason == tool_use:
            结果集 = ⑥.dispatchAll(响应.message.tool_calls, ui)
            for r in 结果集:
                turn.history.append(r.toMessage())    // ★ 失败同样作为 observation
            [L6] 检查六道闸门，超限则以对应 outcome 返回
            continue
        if 响应.finish_reason == stop:
            turn.finalText = 响应.message.content
            return Completed
        if 响应.finish_reason == length:
            return Error                              // ★ 截断不得视为正常完成
```

> **不变式**：
> - 失败**始终**以回喂给模型的 `Message` 表达，不以异常抛出（CR-2、FR-8）
> - `finish_reason == length` **不得**被视为正常完成
> - 依赖以**引用**持有，更换 UI / registry 实现无需重建循环

`LoopHooks`（P-06 观察者的落地形态）：

```
struct LoopHooks:
    onChunk(ChatChunk)          // 流式增量
    onToolStart(ToolCall)       // 工具即将执行
    onToolDone(ToolResult)      // 工具执行完成
    onNotice(string)            // 单向通知
    confirm(string) -> bool     // 权限询问（返回是否允许）
    onError(string)             // ★ 错误须同时完成"回喂模型"与"通知 UI"两件事
```

> **不含渲染相关字段**（光标、颜色、窗口尺寸）的理由：
> 一旦引入，核心层即需知道界面的呈现方式，分层约束随之失效。

#### 5.3.1 `ContextAssembler`（组装 + 预算 + 降级链）

| 项 | 内容 |
|---|---|
| **职责** | 按固定顺序将各来源组装为一次请求；分层预算；超预算时执行**降级链** |
| **对外提供** | `assemble(Turn) → ChatRequest`；`setSystem/setProjectKnowledge/setRepoMap/setTools`；`measure(Turn)`；`config()` |
| **依赖** | ③ ⑤ ⓪ |
| **不做什么** | **不做检索**（仅消费 ③ 的结果）、不决定模型参数（属 ②/⑦） |
| **兑现** | L5（拼接 + 守卫）/ **L7（预算 + 降级链 + `forLayer`）**；③ 的符号抽取在 L8 |

```
契约级伪码 —— 组装顺序（顺序即缓存）
──────────────────────────────────────
function assemble(turn) -> ChatRequest:
    req = 空请求
    req.system   = ⓪L0 系统提示                     // 最稳定，置于最前
    req.messages += L1 项目知识 + L2 仓库地图        // 次稳定
    req.messages += L3 检索命中 + L4 活动文件        // 中相关
    req.messages += L5 历史（可能已压缩）             // 变化快
    req.messages += L6 用户输入                      // ★ 始终最后、始终完整
    req.tools    = tools_                          // ★ 必须设置，否则模型不发起工具调用
    for 每层: 若超配额 → 按"全文→签名→符号名→首行→丢弃"降级
    return req
```

> **两条关键不变式**：
> 1. `req.tools` 必须由 `setTools()` 显式设置 —— 工具表为空时模型不会发起任何工具调用（该缺陷在实现过程中出现过一次）
> 2. L6（用户输入）**始终不被裁剪** —— 它是本轮的语义核心

**降级链（L7 兑现）**：必须设计为链式，而非按长度截断。截断会产生"半个函数"
这类**有害**内容，模型会基于残缺代码作出错误判断。链为：

| 级 | 内容 | 说明 |
|---|---|---|
| 全文 | 原文 | —— |
| 签名 | `extractSignatures()` | 仅保留函数/类型**签名 + 文档首行** |
| 符号名 | `extractSymbolNames()` | 仅保留符号**名称清单** |
| 首行 | 第一行 | 连符号名亦无法容纳时的兜底 |
| 丢弃 | 空 | 宁可缺失，**绝不返回半截** |

> **不变式（L7 增补 INV-14）**：降级链**单调**（每一级占用更少），
> 且**任一级都不返回残缺内容**。由 `--selftest` 的 I-7…I-11 逐级校验。

**★ L7 修正的既有缺陷**：`BudgetConfig::forLayer(L5_History)` 此前为**死代码** ——
历史层并未经过预算计算（L5 仅实现拼接）。L7 使**每一层均实际经过预算**，
这是"已声明却未使用"一类死代码的又一实例（与 L6 的 K-15 同族）。

#### 5.3.2 `Compactor`（五层级联 + 切点铁律）

| 项 | 内容 |
|---|---|
| **职责** | 历史超预算时，按**由低代价到高代价**的顺序逐级压缩 |
| **对外提供** | `compact(history, tokens, …, goalHint) → CompactionResult`；`applyEvents()` |
| **依赖** | ②（L3 摘要需调用模型）、`ISummarizer`、⓪ |
| **不做什么** | 不改工具、不触及 UI、**不决定模型参数** |
| **兑现** | **L7（新增）** |

```
契约级伪码 —— 五层级联（先无代价，最后才有代价）
────────────────────────────────────────────
function compact(history, goalHint) -> Result:
    if 当前 token <= 预算: return 未压缩
    L0 落盘   : 超大工具结果存盘 + 仅留预览            // 无代价

    L3 LLM 摘要: 将老消息压缩为一份**自包含**的交接摘要  // ★ 需调用模型，产生费用

```

**切点铁律（L7 引入）**：

```
function 找切点(history) -> cut:
    从后往前扫描，cut 只能停在 user / assistant 消息之前
    if 候选位置紧邻 tool_result: 越过该位置（继续向前）
    return cut
```

> **不变式（INV-13）**：切点**不得落在 `tool_result` 处** ——
> 否则将产生"孤儿工具结果"，即 L5 的 G8 与 L6 的 K-11 所指的问题（请求返回 400）。
> **K-18**："寻找切点"与"保留最近窗口"是**两个独立约束**，**不得合并为同一段循环** ——
> 合并后切点被推至最前，等价于未保留最近窗口，而日志仍记录"压缩成功"。
> **K-19**：L1 降级只能作用于**已可牺牲**的老历史

| 项 | 内容 |
|---|---|
| **职责** | 将"一批老消息"压缩为一份**自包含**的交接摘要（L3 摘要的算法抽象） |
| **对外提供** | `ISummarizer::summarize(msgs, goal) → std::optional<std::string>`；两个实现 `LlmSummarizer` / `ExtractiveSummarizer` |

> **设计为端口的理由（P-04 策略 / P-02 端口与适配器）**：
> ① **可测** —— `ExtractiveSummarizer` 使压缩的**全部逻辑**在**无 API Key** 条件下

#### 5.4.1 L8 落地的两个文件，以及拆分理由

**抽取独立成文件的两条理由**（均非出于抽象偏好）：

1. **抽取存在两个实现**（tree-sitter / 词法），且需能够**单独对比与替换**
   —— `--symbol-ab` 即依赖该边界存在；
2. **它是本项目范围内唯一需要 `#ifdef` 的位置**。将可选依赖限制在单一编译单元内，
   其余 20 个文件**无需感知** tree-sitter 是否存在。

> ★ **未采用端口（`ISymbolExtractor`）的理由**：端口用于隔离"模块边界**之外**的
> 第二个实现者"（`IModelProvider` / `ISandbox` / `IHttpTransport`）。符号抽取
> **不存在外部实现者** —— 它仅有"有 / 无 tree-sitter 两种编译形态"。因此采用
> **运行时选择 + 编译期兜底**，不采用多态。
> **"是否应增加接口"的判据不是"它将来会不会变"，而是"变化会不会来自该模块之外"。**

### 6.1 ⑥ 工具调用与执行（`ToolRegistry`）

| 项 | 内容 |
|---|---|
| **职责** | 注册工具、校验参数、判定权限、派发执行、过滤输出 |

| **依赖** | ⑧ `IPermissionGate`/`ISandbox`、① 插件、⓪ |
| **不做什么** | 不管理循环、不修改上下文、不调用模型 |
| **兑现** | L4（派发）/ L6（权限门）/ **L7（输出落盘 L0）** |

```
契约级伪码 —— 派发管线（五步，顺序固定）
──────────────────────────────────────────
function dispatch(call, ui) -> ToolResult:
    e = find(call.name)
    if e == null: return error(call.id, "未知工具: " + call.name)

    if not 校验(call.args, e.def.inputSchema):
        return error(call.id, "参数不合法：..." + 期望的 schema)   // 回喂给模型修正

    d = gate.evaluate(e.def, call.args)
    if d == Deny:  return error(call.id, "被拒绝：" + d.reason)     // ★ 必须给出原因
    if d == Ask and not ui.confirm(d.prompt): return error(call.id, "用户拒绝")

    r = invoke(e, call.args)                                     // 内置或插件
    r.content = sanitizeUtf8(r.content)                          // ★ 输出卫生
    r = maybePersistLargeResult(r, e.def, dumpDir)               // ★ 大结果落盘
    return r

function dispatchAll(calls, ui) -> ToolResult[]:
    return [dispatch(c, ui) for c in calls]                       // 按 id 配对，不按调用顺序
```

> **不变式**：
> - 管线顺序固定：**注册 → 校验 → 权限 → 执行 → 输出过滤**
> - `dispatch` **不抛出异常**（CR-2），一切失败均表达为 `isError=true` 的结果
> - 结果按 `callId` 配对，**不按调用顺序**

`IUIPort`（端口④，仅有两个方法）：

```
class IUIPort:
    confirm(prompt) -> bool     // 阻塞式询问；返回是否允许
    notice(msg)                 // 单向通知

class NoUI : IUIPort:           // P-17 空对象
    confirm(_) -> false         // ★ 安全默认：无 UI 时拒绝，而非放行
    notice(_)  -> 不执行任何动作
```

> **方法数量恰为二的理由**：方法过多会使渲染逻辑渗入核心层；方法过少则无法表达"需要人工批准"。

#### 6.2.1 ★ L9 落地时的三个判断

**① 刻意不为 `IUIPort` 增加方法（本模块最重要的一个设计判断）**

| 阶段 | 接口 | 理由 |
|---|---|---|
| L2 | `confirm()` | 仅支持"询问" |
| L5 | `+ notice()` | 循环需能报告"发生了什么" |
| **L9** | **不增加** | ★ 见下 |

> `IUIPort` 回答"**核心需要人做什么**"（confirm）；
> `LoopHooks` 回答"**人需要知道核心做了什么**"（事件流）。
> **向 `IUIPort` 中加入"输出流式文本"，等价于让核心层知道界面需要什么 —— 分层约束被破坏。**
> L9 采用后者（`LoopHooks`）；该结构自 L5 起即已就位，6 个回调足以表达 8 种 `ChatChunk`。

**② 渲染器不采用端口（`IRenderer`）**

> 端口用于隔离"模块边界**之外**的第二个实现者"。渲染器仅有 TTY / 非 TTY 两种形态，
> **变化不来自该模块之外** → 两个 `.cpp` 实现同一头文件，运行时选择。
> 判据（与 L8 的 `symbol_extract` 相同）：**"是否应增加接口"问的不是"它将来会不会变"，
> 而是"变化会不会来自外部"。**

**③ ★ 非 TTY 必须自动降级，且降级是**硬要求**而非可选项**

> 画布模式下每帧携带 `ESC[...m`。而**全部验证用例均依赖"将 stdout 重定向至文件后检索"** ——
> 一条漏网转义即可使某条断言失配，且**错误在另一个用例中显现**。
> 处置分三层：① 出口按 TTY 分流（`writeFrame()` 为**唯一**一处）；
> ② plain 后端不产生 ANSI；③ **增设元用例守护**（C27：重定向后 ESC 计数为 0，**两个后端均测**）。
> **判据**：验证体系本身亦是一套产品，同样需要回归测试。

### 6.3 ⑬ 测试与评估

| 项 | 内容 |
|---|---|
| **职责** | 运行回归集、计算通过率、汇总成本与步数 |
| **对外提供** | 回归运行入口、报告生成 |

**L12 兑现形态（`--regress <regress.jsonl>`）**

| 项 | 内容 |
|---|---|
| 输入 | 每行一条用例：`{"name":..., "pass":1, "cost":N, "steps":N}` |
| 输出 | **通过率 + 平均成本 + 平均步数**，**三者必须同时出现** |
| ★ 拒绝规则 | 任一用例缺 `pass`/`cost`/`steps` 中任一项 → **exit=2，且连通过率都不输出** |

> ★★ **"缺一项即拒绝"而非填 0 补齐通过率的理由：**
> 填 0 会使 `cost=0` 呈现为"成本很低"，从而使报告整体偏乐观 ——
> **残缺的通过率比没有通过率更危险**。这是本模块唯一一条硬规则。
>
> ★ 三个数必须**同时**报告，是对古德哈特定律的唯一有效应对：
> 仅报通过率 → 会奖励"暴力重试"（多次尝试后通过，成本翻倍而不可见）；
> 仅报成本 → 会奖励"不执行任何动作"（不调用工具自然便宜）。
> **使舞弊方向互相牵制，是唯一可行的办法。**
>
> ★ 上述三句由 `--regress` 自身打印在报告末尾 ——
> 契约写入本文档无人阅读，**写在查看报告者眼前才会发挥作用**。
